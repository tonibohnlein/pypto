# 单核 AutoSync 架构

AutoSync 为 A2/A3 单个核上复用物理存储的异步操作建立顺序。即使两个 tile 的 SSA 名称不同，后一次加载覆盖目标存储时，前一次存储操作仍可能正在读取该 tile。因此 AutoSync 在最终存储放置之后运行，以识别物理重叠。对每条可行执行路径，它保留实际执行的载荷操作（payload）、载荷顺序和程序员编写的通信。发射的循环和条件分支可以改变。

本文定义分支的架构基线。**已实现**指当前编译器的行为，**提案**指两条规划路径共用的区域接口及后续的资源计划边界。较早的架构和覆盖计划记录了各自阶段的状态。[区域架构](39-regional-sync-architecture.md) · [集成计划](41-general-autosync-architecture-plan.md)

## 从访问到可执行计划

1. **构造需求。** 对每次允许的执行，较早的冲突访问必须在较晚载荷发射前完成。冲突包括物理字节重叠的写后读、读后写和写后写，具体以选中实现的原生保证为准。还须计入已给定的顺序约束。精确路径在其支持的访问模型和原生顺序下约简需求。保守路径沿分支和循环回边传播可能尚未完成的访问，以及已保证传递的完成信息，并涵盖零次迭代。
2. **选择记录点与等待点。** 一个逻辑完成凭证（token）可供多个消费者使用。流水线前缀记录捕获该位置之前在本流水线上发射的工作，以及此前已获取的完成信息。消费者必须在首次冲突发射前取得所需前缀。提前记录可以释放后续独立载荷，但仍须满足所有曾依赖原前缀的后续消费者。同流水线冲突可能需要本地屏障。
3. **分配并发射。** 硬件等待会消费一次发布。在同一方向和执行实例上复用事件 ID，必须证明上次消费先于下次发布。分配须计入原生预留、生成的反向确认、跳过的访问以及调用结束时的事件闭合。增加顺序或受条件保护的命令时须重新验证可行性。拒绝时按所有权边界丢弃候选改动。按函数管理所有权时，PTOAS 可以开启插入并跳过已显式同步的函数。[物理实现](15-physical-demand-realization.md) · [RealizeSync](../passes/59-realize_sync.md)

**已实现路径。** 公开 token 路径为 `InsertSync → OptimizeSync → LowerSync`，由 `RealizeSync` 协调。降低阶段解释实际 token 并进行物理规划。对端规划还有直接分配事件的有限路径，以及导出逻辑前缀的结构化路径。存储、原生实现、载荷顺序、控制流或目标发生变化时，所有依赖该条件的证明都须重新建立。[逻辑阶段](../passes/60-logical_sync_pipeline.md) · [对端规划](../../../../src/ir/transforms/utils/peer_local_plan.cpp)

## 区域与父级之间的契约

草稿第 8 节区分选择性组合、保守前缀入口同步和区域完成三种机制。精确选择性构造（第 5 节）对写入不会再细分的每个物理存储类，导出首、末写者，各流水线在首次写入前的首个读者，以及在末次写入后的最后读者。若区域内没有写者，则导出各流水线的首、末读者。子区域还提供边界执行实例的身份，并支持查询发射和完成事件之间的先后关系，其中包括原生顺序。父级据此构造并约简跨区域需求。保守构造（第 6 节）允许父级在满足入口前提时保留已闭合子区域的命令，并根据各流水线的可靠访问摘要添加入口同步。若要利用内部等待删除入口同步，就须证明该等待在冲突载荷发射前交付所需的传入完成信息。区域完成还可传递闭合片段在共同完成点前后的访问摘要。分支中的逐流水线完成摘要记录的是另一组事实。调用方仅请求当前证明所需的能力。

| 边界 | 有限与结构化规划共用的接口提案 |
| --- | --- |
| 入口与首次使用 | 标明可能访问的物理范围、发射流水线，以及原程序中可能首先与传入工作冲突的发射位置。在每个位置描述内部记录与等待在所有可达路径上保证交付的传入完成信息。每次记录都关联到相应生产者的那次执行。 |
| 出口与重复执行 | 导出各流水线已确定取得的完成信息和可能仍在进行的访问，包括每个轮转槽的读者。合并分支时保留任一分支可能留下的义务，只保留所有到达路径均成立的保证。须涵盖跳过的迭代、槽轮转和尾段使用。 |
| 物理资源 | 完成资源规划后，导出定向事件占用、预留、生成的反向确认和跨边界的消费义务。父级若改变交接，必须重新检查存储顺序、事件匹配、复用的因果顺序，以及在原通信协议假设下能否推进。 |

**当前实现。** 紧凑精确分析选取边界读写者、约简跨界需求，并查询发射与完成事件之间的可达性。保守分析已有按流水线投影的出口摘要、保留子区域的资源信息，以及用于合格直线内联子区域的逐发射入口检查。入口检查读取逻辑命令，在父级控制流图上固定其余同步，共同验证所有候选删除。[紧凑区域组合](../../../../src/ir/transforms/utils/compact_sync_analysis.cpp) · [完成摘要](../../../../src/ir/transforms/utils/conservative_sync_completion.h) · [入口和出口分析](../../../../src/ir/transforms/utils/conservative_sync_dataflow.cpp)

**共同契约提案。** 每项结果标明物理存储划分、原始执行实例坐标、允许的执行上下文，以及查询描述的顺序（载荷必需顺序、选定的逻辑顺序或已发射命令的顺序）。选择器可以返回实例、证明实例不存在，或报告缺少证据。已存在端点之间的可达性另行查询。通过这一接口复用已有的精确选择器和保守摘要。若路径在结构上适用却缺少所请求的证明，则返回未满足的义务。[区域查询契约](39-regional-sync-architecture.md)

**入口同步的适用条件。** 保留的每次区域执行都须在其内部完成逻辑事件配对，须有合法的入口插入点和已就绪的条件值，并须保护给定的非存储前提。导入物理计划时还须证明事件归属和复用前的消费顺序。例如，若一次迭代的 SET 由下一次迭代的 WAIT 消费，可以考虑保留整个循环，而逐次迭代添加入口同步则不满足配对条件。若所选边界不满足条件，应尝试符合条件的外层边界或报告未满足的义务。

### 两个验收示例

**Prefill 合并。** 三次加载填充当前输入 tile。在累积分支中，另三次加载写入不相交的 tile，然后首个向量消费者 `TMAX` 才发射。该处已有的 MTE2→V 等待覆盖两组加载。若重放证明后续使用与事件复用也安全，父级即可删除入口的一对标志命令和一个 MTE2 屏障。每次实际累积都释放九对加载完成到加载发射的约束。让加载目标与预取数据重叠时，必须恢复同流水线顺序。初始化和跳过工作分别验证其他路径。[带条件的别名回归](../../../../tests/ut/ir/transforms/test_automatic_sync_children.py)

**双槽接收流水。** 若本地有两个 Mat 槽，从零计数的第 `k` 次实际 pop 写入 `base + (k % 2) * slot_stride`。即使游标继续推进，接收 tile 的视图也保留该次绑定。读取槽 0 的 MTE1 搬运必须在下一次覆盖槽 0 的 MTE2 pop 之前完成，包括 pop 位于尾段的情况。Free 结束逻辑借用，此前发射的异步读者仍可能在运行。跳过 pop 时游标保持原位。当前规划器可在最后读者之后交付完成信息。更精细的方案可以在该处记录，到首次实际覆盖才等待，前提是对每条路径证明槽位选择及事件复用安全。验收既要验证读者先于覆盖，也要验证无关搬运仍可与覆盖重叠。[槽位顺序回归](../../../../tests/ut/ir/transforms/test_peer_loop_slot_order.py)

## 与同步草稿的对应

依据为 *Synchronization for Reused Physical Storage* 的 `7f2f244` 版本，正文第 3–8 节位于 `paper/sections/`。第 3–5 节固定载荷程序、定义完成到发射的必需关系并约简精确需求。直接插入得到最小元的结论有前提，包括不可省略的同流水线需求连接相邻执行的载荷。第 6 节给出保守覆盖，并说明利用内部交付删除子区域入口同步所需的接口强于访问集合的简单并集。第 7 节区分固定计划的分配与可能增加顺序的修复。第 8 节组合逻辑和物理两个阶段。分支实现了这些构造在已验证范围内的实例。对于所有支持的保守计划和有限资源计划，全局极小性仍未得到证明。[草稿仓库](https://github.com/tonibohnlein/synchronization_draft)

比较计划时固定载荷顺序、操作数、物理放置、别名假设及调用边界。对执行 `e`、消费者实例 `b` 和流水线 `p`，`K(e,b,p)` 是 `b` 发射前必须完成的最后一个 `p` 上载荷的序号，空前缀取零。草稿将必需的前缀记为 `K₀`，将计划 `Σ` 建立的前缀记为 `KΣ`。若一个计划的每项均不大于另一计划的对应项，则前者支配后者。已知必需顺序的前缀时，可对差值求和衡量额外顺序。和 stock 比较时，分别报告仅各自增加的约束对。允许 pop 提前但推迟后续加载的计划可以有更小的总数，而两个计划仍不可比。标志、屏障和条件分支分别统计静态位置与实际执行次数。延迟需要设备计时。

## 与 RFC #3375 的对应

| RFC 边界 | 当前分支与演进方向 |
| --- | --- |
| 捕获与规范化 | RFC 中，`with pl.sync.record(after=t) as done:` 包含操作体，可选的 `after` 约束入口，`done` 表示操作体的完成。不同流水线的 token 可以合取。分支提供流水线前缀记录和同流水线合取。用户记录与自动约束的一般组合仍待实现。当前本地规划已能保留原有传输命令。 |
| 依赖构造与简化 | 分支在放置后构造需求并简化逻辑 token。RFC 将区域规范化、依赖插入、局部规范化和控制流简化分开，再执行一次局部规范化。最小需求约简属于分析阶段。RFC 的局部规范化使用 token 等价关系。 |
| 绑定、规划与降低 | 分支在资格检查时选择原生流水线，在物理降低或有限对端路径中规划资源。RFC 由 `BindSyncPipes` 绑定流水线，`PlanSyncResources` 规划资源，`LowerSync` 发射已验证的放置结果。共同的区域契约是下一步。包含有序动作和条件、可序列化且限定目标的放置结果是后续里程碑。 |
