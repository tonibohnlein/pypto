## 预检与命令计数修正

AST 摘要错误确实与 Python 版本有关：3.14 默认省略空字段，旧版本保留。
显式保留空字段后得到设备上的 d12d89fd 摘要；本机 3.11、3.12、3.14 均通过。
原始与适配代码的结构相等检查、源文件哈希仍保留，没有放宽负载或控制验证。

归档所谓 executed_set 实际统计可达函数中的静态站点，没有执行循环或守卫。
互斥守卫下重复的命令不能累计为同一工作单元的动态通信。PTOAS 尾函数实际选择
ALL 分支，另一分支中的 MTE3 到 S 标志对并未执行。

保留原始 C++ 标量控制的主机计数显示，H5120、L1 下：输出投影每工作单元
PyPTO 为 357 对、PTOAS 为 369 对；gate/up 单输出块为 357 对比 411 对，
双块为 719 对比 813 对。四个 band 均相同，PyPTO 动态通信更少。

但 PyPTO 源级条件判断更多：band2 双块执行 7364 次 if 条件，PTOAS 为 80 次。
这不是优化后设备指令数或延迟。原因是共享切点上的独立激活情况重复发射守卫；
后续可在保持端点、ID、匹配及通信次数的前提下合并等价命令与精确守卫并集。
本次没有修改发射器或分配算法。

## 性能解释

Qwen 的合并工作单元中位数改善 0.8–4.4%，不能从微小 matmul 的百分比推断更大收益。
同步只有阻塞关键路径才影响延迟，计算、访存重叠及额外控制工作都需测量。

30 个调用跨度批次均有改善。两个合并工作单元中位数稍差，但没有发现某核心在
全部三个批次都退化；记录缺少逻辑块身份，不能断言稳定的工作单元回归。
调用跨度包含设置时间，与排除设置时间的 kernel-duration-us 指标不同。
反转顺序的第二批次也并非总在第一、第三批次之间，因此不能排除顺序漂移。

尾部 ALL 排空是合理假设，未经相同计划和相同边界的对照实验隔离。
运行时 stream_wait 的成功不证明通用原生返回语义。先统一边界合同、记录块和阶段
身份、检查标量指令及管道停顿，再评估更大的收益；不可按静态屏障数外推延迟。
