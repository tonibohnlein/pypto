# 同步代码展开核算

剩余开销来自多个层次。在已检查的小规模执行中，PyPTO 对每个跨流水线最小覆盖
执行一次交接，但这不代表静态命令代码或控制计算已经最小。本次核算沿需求族、
逻辑令牌（logical token）、分配和发射命令逐层检查。生产算法和输出保持不变。

基线为 `4f5fdfeada1085841de6cb5bfd7637d391a9663e`。
[回执](../../../en/dev/ir/sync-expansion-accounting.json) 固定扩展、诊断源码、输入、
测量和复用的比较证据。本工作承接[基于插入位置的同步控制](26-cut-aware-sync-control.md)。

## 表示在哪里增长

Qwen gate/up，band 2、H=5120 的调用划分为四个情况：

| Block 范围 | 段数 / 载荷站点 | 内部需求 | 跨段需求族 | 导出需求族 | 每次选定调用执行的交接 |
| ---------- | --------------- | -------- | ---------- | ---------- | ---------------------- |
| 0–4 | 8 / 34 | 16 | 23 | 39 | 719 |
| 5–11 | 4 / 17 | 8 | 9 | 17 | 357 |
| 12–18 | 4 / 17 | 8 | 9 | 17 | 357 |
| 19–23 | 8 / 34 | 16 | 23 | 39 | 719 |

核算将数学导出的需求族多重集，与实际逻辑令牌程序解析出的需求族及物理分配器的
输入逐一比较。原始端点坐标和重复轴一致。只有一个取值的笛卡尔轴贡献零位移，
因此允许规范化消除；其他轴和需求族重数保持不变。这些层之间没有需求族倍增。
这些 Qwen 情况中的每个需求族均只分配一个 ID。

四个互斥情况合计 112 个需求族实例。逻辑 IR 包含 29 个 `sync.record`、112 个
`sync.wait`、110 个 `sync.completed` 和十个循环传递令牌。多个记录可共享来源
位置；completed 令牌是 SSA 占位值，不是硬件命令。`OptimizeSync` 不改变这些数量。

物理 IR 有 86 个 SET、76 个 WAIT 和 234 个分支，其中 232 个是插入的守卫，两个
来自原程序。最大守卫只有七个表达式节点，共有 61 个不同的守卫表达式。问题主要
是重复的小控制及情况相关的命令序列，而非一个巨大的布尔公式。

源码路径如下：

- `invocation_sync_analysis.cpp` 的 `AnalyzeSyncInvocation` 划分调用并保留各情况分析。
- `scoped_logical_sync.cpp` 的 `Append` 将带作用域的需求族传入令牌 IR。
- `token_sync.cpp` 的 `OptimizeSync` 验证逻辑同步，目前不做优化。
- `structured_token_sync.cpp` 的 `LowerStructuredLogicalSync` 解析实际令牌，分别分配各情况。
- `physical_sync_realization.cpp` 的 `ScopedGuards`、`Commands` 和
  `EmitAssignedSyncCases` 构造端点守卫、字面 ID 选择和原始插入位置的完整有序命令序列。
- `EmitSyncCommandCases` 在已证明的执行域内共享完全相同的序列，不共享不同序列的公共子序列。

各情况独立选择的合法 ID 会阻碍共享。例如，原始语句序号 65 的同一编码来源端点，
在 block 0–4、19–23 中使用 ID 1，在 5–11 中使用 ID 0；方向为 0→3，编码数量为 40。
加入 ID 之前有 78 个端点描述，加入后有 102 个。这些描述省略了情况谓词及配对端点，
因此 **78 既不是已证明的下界，也不是可安全合并的计划**。

## 执行的控制与其他内核

上述大规模 gate/up 在检查的两个边界执行中（block 0/layer 0 和 block 23/layer 1）均有：

| 条件依赖 | 求值次数 | 假值次数 |
| -------- | -------- | -------- |
| 仅启动情况 | 2,882 | 1,921 |
| 迭代坐标 | 1,996 | 965 |
| 原始条件 | 80 | 78 |

4,958 次条件求值中，58.1% 仅依赖启动情况。即使共享标量值，也可能重复测试不变量。
依赖分类是描述性统计，不允许据此移动命令、求值被跳过的表达式或跨调用重置提升计算。

| 用例 | 各情况需求族实例总数 | 静态 SET / WAIT | 含原始控制的分支数 |
| ---- | -------------------- | --------------- | ------------------ |
| Matmul / accumulation | 4 / 10 | 4/4；10/10 | 0；0 |
| DDR split-K | 15 | 15 / 15 | 18 |
| Vec / softmax | 3 / 6 | 2/2；2/2 | 0；0 |
| Rotating，7 次访问 | 3 | 9 / 9 | 20 |
| Crossings | 7 | 14 / 14 | 36 |
| Collective / nested | 2 / 7 | 2/2；7/7 | 4；10 |
| 库 matmul / GEMM | 5 / 7 | 5/5；7/7 | 0；8 |
| Qwen output H=5120 | 17 | 17 / 17 | 27 |
| Gate/up band 0,1,2,3 H=5120 | 73,90,112,90 | 60/55；66/55；86/76；75/71 | 159,171,234,207 |

Vec 和 softmax 另有一个和四个同流水线屏障，所以需求族数量不一定等于标志对数。
静态数不等于执行数；此前设备报告的 73–112 对 46 比较是静态站点数。

Qwen output 有 26 个依赖迭代的守卫和一个原始条件。检查的活跃执行求值 868 次迭代
条件和 40 次原始条件。仅共享启动情况无法解决它的开销。Rotating 用例每个需求族
分配三个 ID，因此三个需求族变成九个 SET 和九个 WAIT 站点。其选定执行有 14 次纯
迭代条件及 66 次迭代/取模条件求值，这是另一类选择器和阶段问题。

Rotating 次数为 7、70、7,000 和 1,000,000 时，均保留三个需求族、九个 SET/WAIT
站点和 20 个分支。Nested 次数为 (2,3)、(2,1000)、(1000,3) 和
(1000000,1000000) 时，均保留七个需求族、七个 SET/WAIT 站点和十个分支。
这些用例对循环次数保持紧凑；这不约束静态阶段、划分及独立变化接口的增长。

## 顺序与必要通信

28 个核算用例全部完成。21 个小规模执行独立从原始 IR 构造访问、原生顺序、要求
闭包和最小覆盖，再检查发射命令。匹配闭合、图无环、标志复用具有因果路径，载荷
顺序等于选定要求顺序。执行的 SET/WAIT 对数等于跨流水线覆盖数。这支持当前直接
协议，不是所有可能协议的通信下界。

生产源码未变且输入及源码哈希一致，因此沿用上一轮生成 C++ 的顺序检查。本次重新
执行 15 个已有主机跟踪程序以计数。下列顺序证明复用旧证据，不是新设备测量：

| 用例 | 执行标志对 PTOAS → PyPTO | PTOAS 内部屏障 | 多余完成到开始关系 PTOAS → PyPTO |
| ---- | ------------------------ | -------------- | -------------------------------- |
| Matmul / accumulation | 4→4；10→10 | 0 | 0→0 |
| DDR split-K | 25→19 | 12 | 21→0 |
| 库 matmul | 5→5 | 1 | 1→0 |
| 库 GEMM | 28→22 | 0 | 0→0 |
| Qwen output H=512，活跃 worker | 45→33 | 21 | 32→0 |
| Gate/up H=512，band 2 | 93→71 | 42 | 202→0 |
| Gate/up H=512，其他 band | 51→33 | 21 | 56→0 |

完整关系集合比较确认这些执行上顺序相同，或只删除要求而不添加要求，不仅是数量
减少。指标使用论文的完成秩剖面 K(b,p)，在前缀前提成立时与显式多余关系对核对。
PTOAS 每个已检查跟踪还执行一个返回 ALL 排空操作，它与内部载荷顺序分开计算。
PyPTO 不发射它仍需调用边界契约支持。PTOAS 使用八个 ID，PyPTO 使用六个；这不是
物理 ID 最优性结论。

访问检查独立于编译器需求生成，但仍假定已限定的操作足迹、布局及原生命令发出
模型。H=5120 用例在这里检查模式和控制，未做完整展开的独立命令图证明。旧回执的
六个 C++ 比较用例仍明确不可用。本次没有新的设备或 C++ 生成活动。

## 成本、复现和后续实现

回执分别记录普通 `RealizeSync`、独立 Insert/Optimize/Lower 调用及诊断重建。
它们来自不同运行，不能相加，也不能把审计重建计入生产开销。时间是单次主机观测，
不是加速证据。独立检查器的展开不计入生产计时。诊断从固定输入重建分析，不读取
实际生产 owner 的私有存储。

| 用例 | 普通生产路径，ms | 独立 Insert / Optimize / Lower，ms | 单独审计，ms |
| ---- | ---------------- | ---------------------------------- | ------------ |
| Rotating，7 次访问 | 1.42 | 0.44 / 0.05 / 0.85 | 0.84 |
| Qwen output H=5120 | 5.06 | 1.52 / 0.31 / 3.60 | 4.02 |
| Gate/up band 2 H=5120 | 36.35 | 6.75 / 1.27 / 30.62 | 36.22 |

Lower 包括令牌解释、分配和发射；这些时间没有隔离分配器，也不证明其内部哪一步主导。

11 个聚焦测试通过，包括单值轴规范化及已执行条件归因。Ruff 和聚焦类型检查通过。
此前 1,551 个测试的结果属于旧证据，本次诊断变更没有重跑全套测试。完整需求族清单
保留在磁盘核算产物中，仓库回执记录其哈希及各用例摘要。

下一阶段应优化现有令牌到命令路径：

1. 保留情况分支及端点身份，在合法插入位置共享决策和有序命令子序列。先处理已经
   分配相同 ID 的命令，不要求新分配策略。若在 `OptimizeSync` 合并逻辑等待，必须
   在实际令牌程序中保留捕获语义、守卫可用性及发生实例身份。
2. 将情况内 ID 重命名作为单独认证机会。一致的方向双射必须保留所有使用及保留
   资源；独立修改一个端点无效。当前计数不是这个证明。
3. 用已限定的阶段决策处理首/末次及余数测试，涵盖零次、短循环和尾部。不为消除
   不变条件而克隆完整载荷体；不支持的情况继续走现有路径。
4. 每次变化检查有序命令跟踪（或单独证明的协议等价）、完整前置关系包含、匹配及
   因果复用。同时测量静态站点、值定义、假条件求值及构造工作。

目标是减少紧凑精确需求描述周围的重复，不是删除必要交接、为缩小代码增加屏障，
也不意味着剩余守卫都已证明必要。
