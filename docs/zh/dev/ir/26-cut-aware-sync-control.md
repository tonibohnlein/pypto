# 基于插入位置的同步控制与顺序质量

本阶段延续[紧凑同步控制](25-compact-sync-control.md)。基线是提交
`3f437376e4188a31e5ddf5dc5e284dc99a9d742b` 上已经评审但尚未提交的检查点，
不是该提交本身。[机器可读记录](../../../en/dev/ir/cut-aware-sync-control.json)
固定了两份工作树、扩展、输入、命令和结果。本次不改变需求分析、令牌、分配算法、
硬件豁免规则或同步协议。

## 表示问题

最少需求、较小命令代码以及较低动态控制开销是三个不同目标。最少需求也可能具有复杂
的可执行选择器；多个记录也可能重复相同的小条件。因此只统计命令数或不同表达式数
无法充分衡量同步成本。

此次主要重复来自物理命令的分情况生成。每种情况保存了块编号区间和完整命令序列，
但插入位置没有保留区域树已经证明的执行域。因此，即使原位置在某些工作块上不能
执行，仍会重复生成条件。多个条件也会重新计算相同的归一化迭代商。

修复位于 `src/ir/transforms/utils/physical_sync_realization.cpp`，由生产令牌
降低和诊断入口共同使用。不添加 Qwen 专用识别或新的候选分析。

## 契约与正确性

每个原始载荷前后的位置保存一个**可能执行域**：有序、不相交的闭区间。它是上界，
未知意味着整个准入调用域。只有已有区域树中的零次重复证明才能减去区间；缺少载荷
记录或命令清单为空都不能作为缺席证明。

遍历原始结构化语句，将这些事实传递到插入位置，不遍历载荷表达式 DAG。只比较相邻
情况的完整命令序列，并保持 SSA 身份。仅当可能执行域不与间隙相交时，才允许跨越数值
间隙合并。位置会执行但无需命令时，间隙仍被保留。载荷前后位置分别处理，命令不会
越过载荷或原始控制边界。

对每个真正到达该位置的执行，选择的命令序列与原来相同。改变已证明缺席的执行不会
运行任何新增命令。完整有序序列相等保证命令、次数、方向和物理 ID 不变。结构比较
不支持时保留原情况。

接下来的局部处理减少标量计算：

1. 使用现有算术分析器，根据原始常量、正步长循环范围简化所生成的条件。不修改载荷
   控制，不假定新动态范围。不支持比较时保留条件。
2. 在局部作用域共享重复 INDEX 比较和变量除以正常量的归一化商。仅接受严格、纯粹的
   INDEX/BOOL 树，排除调用、短路表达式和不安全除数。临时值在首次实际求值处定义，
   保留原守卫和调用范围。分支使用独立表，不提升到循环前，不让分支私有值逃逸。
   名称按原始源码顺序分配，序列化往返后也保持确定性。

使用现有结构化 IR、`arith::Analyzer`、结构哈希/相等比较和同步名称分配器。这不是
通用 CSE 或推测执行。哈希碰撞及比较不可用只损失共享机会，不影响已接受计划。

因此变换保留完整有序命令轨迹。正确性不依赖较低的额外先决条件计数，也不依赖新分配
证明。已有原生指令和调用边界前提仍需单独满足。

## 先测量顺序，再比较代码量

`sync_order_metrics.py` 使用独立构造的载荷闭包。对每个目标开始事件和源流水线计算
论文中的最大必需完成序号 `K(b,p)`。先检查完成前缀前提，再验证序号差之和等于额外
完成到开始事件对的数量。另行检查全部事件对覆盖。

比较保留实际新增和删除的先决条件对。相同计数可以对应不可比较的计划；较低计数本身
不证明包含关系。测试覆盖这两点。末尾 ALL 单独计数：它可能影响调用完成，却不增加
内部载荷先决条件。

`sync_cpp_order.py` 将受支持生成 C++ 的控制提取为主机轨迹，保持标量 ABI 类型以及
有符号/无符号提升规则。命令图检查实际 SET/WAIT/屏障位置、匹配、无环性和消费先于
再次发布的因果路径，不人为添加复用边来使验证通过。允许初始化 SET；ALL 不消费通知。

载荷效果来自原始 IR 访问预言机，而不是编译器需求记录；宏序列必须与原 IR 一致。
这独立于需求规约，但依赖已限定的宏降低、布局、原生流水线和标量发令契约。它不证明
任意 C++ 载荷等价或原生正确性。不支持的导出和轨迹语法明确报告不可用。

## 结果与成本

完整同步测试通过 **1,551 项**（36 条弃用警告）；最终定向测试通过 **30 项**。
评审接受了实现、命令图检查器和报告；类型、格式和文档检查通过。28 个原始输入哈希
与基线一致。Qwen 两个层的全部工作块及此前有界内核，共 **477 条**完整命令轨迹
全部一致。另有九个小实例独立比较载荷顺序。
28 个案例的新旧版本均生成 C++。

| 案例 | 物理 IR 分支数，之前 → 当前 | C++ 字节，之前 → 当前 |
| ---- | --------------------------- | --------------------- |
| Qwen output H=5120 | 27 → 27 | 17,499 → 17,599 |
| Gate/up band 0 H=5120 | 187 → 159 | 见记录 |
| Gate/up band 1 H=5120 | 242 → 171 | 见记录 |
| Gate/up band 2 H=5120 | 312 → 234 | 53,460 → 46,104 |
| Gate/up band 3 H=5120 | 242 → 207 | 见记录 |
| DDR split-K | 18 → 18 | 11,440 → 11,361 |

Gate/up band 2 在第 0 层全部 24 个块上的条件求值从 109,734 降到 82,466。
条件表达式访问从 464,146 降到 348,102，而标量值表达式访问从 3,154 增到 12,514。
两者合计下降 22.8%；执行的 12,188 次 SET 不变。Qwen output 分支数不变、C++ 增加
100 字节，但相同结构计数从 94,080 降到 79,680。因此不声称所有源码或临时值都减少。
嵌套案例源码也略有增长（例如 6,898 → 6,943 字节），命令和分支位置保持不变。

这些是源码表达式出现次数，包括语法上存在的短路操作数，不是硬件指令计数。标量定义
和求值与条件一起报告，避免把计算移入临时值伪装成消除计算。

独立 PTOAS 比较验证十个支持案例。基础 matmul、累加和库 GEMM 的先决条件相等。
验证过的 DDR split-K、库 matmul 和 Qwen 执行中，PyPTO 删除先决条件且不新增。
记录保留各配置和证据，包括空边界工作块。另六个案例有明确的导出/轨迹适配器限制，
不是六个编译失败。PTOAS 使用八个可用 ID，PyPTO 使用六个，不据此声称最少 ID。

旋转循环次数增长到 1,000,000，仍为 20 个分支及 9 个 SET/WAIT 静态位置；嵌套次数
增长到 (1,000,000, 1,000,000)，仍为 10 个分支及 7 个 SET/WAIT 位置。零次旋转
案例保留原来的事务式委托。通用执行域测试将启动界限增到 7,000,000，不枚举工作块。

构造计数分别记录传播区间片段、相邻情况比较、合并、条件简化、值共享和表达式检查。
结构比较/哈希遍历及已有算术分析需要另计；`control_expression_visits` 不包含这些
库的内部工作。嵌套域传递取决于传播区间片段，而不只是不同源码节点。不声称对源码
大小或不同 DAG 节点数统一线性。生产耗时不包含另外请求的诊断分析。单次测量仅描述
成本，不证明加速。

## 复现

使用固定的 Linux 扩展和 PTOAS v0.72；不要加载过期 macOS `env.sh`。启动器需要
PATH 中的 Python 3.11；扩展使用 Python 3.14。其他密集任务占用另一工作线程时串行运行。

```bash
source .claude/skills/testing/load-env.sh
export PYTHONPATH="$PWD/python:$PWD"
export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 PYPTO_CODEGEN_MAX_WORKERS=1
export PTOAS_ROOT="$PWD/build-py314/physical-sync-prototype/ptoas-v072"
PYPTO_TOKEN_PY311=$(dirname "$(readlink -f /home/toni/.local/bin/python3.11)")
export PATH="$PYPTO_TOKEN_PY311:$PATH"
cmake --build build-py314 --parallel 1
/usr/bin/python3 -m tests.ut.ir.transforms.qualify_sync_control \
  --baseline build-py314/guard-control/final \
  --output build-py314/cut-control/final --emit-cpp
/usr/bin/python3 -m tests.ut.ir.transforms.qualify_sync_order \
  --physical build-py314/cut-control/final \
  --output build-py314/cut-control/ordering
```

基线产物和源码快照保存在磁盘工作区。构建本次变更前，用上一检查点的驱动及扩展重建。
记录固定了哈希及完整测试文件清单，不放宽超时或预期。较早一次测试因 PTOAS 启动器
错误而停止，单独保留，不算作通过结果。

## 论文含义与后续限制

| 已建立结果 | 限制 | 合适的结论 |
| ---------- | ---- | ---------- |
| 独立检查有界配置和先决条件包含关系 | 限定访问/原生模型，有限执行 | 顺序质量需测量，不能从命令数推断 |
| 情况合并与局部值优化保持完整有序轨迹 | 原有实现与分配前提 | 控制可以缩小而不改变需求或物理协议 |
| 已测循环次数不扩大生成模板 | 静态阶段、区间片段和接口仍可增长 | 循环次数紧凑性不是通用代码量界限 |
| 分别报告源码和动态控制成本 | 无新设备实验 | 不推出设备加速或返回边界证明 |

修改重复命令族、减少令牌、合并不同协议或选择新 ID 分配，都需要另行证明匹配、顺序
和复用。本次保持这些决定不变。剩余条件区分不同命令或执行域，或超出现有证明规则；
并未证明它们全都必要。更广泛的控制最小化是具有独立表示和成本界限的次级优化目标。
