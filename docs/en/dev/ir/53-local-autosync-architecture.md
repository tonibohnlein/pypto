# Single-core AutoSync architecture

AutoSync orders asynchronous operations that reuse physical storage on one A2/A3 core. A store can still be reading a tile when a later load starts overwriting it, even if the two tiles have different SSA names. AutoSync works after final placement so it can see that overlap. For each feasible execution it preserves which payloads run, their order and the programmer-authored communication. The emitted loops and guards may change.

This page defines the design baseline for the branch. **Implemented** describes the current compiler. **Proposed** marks the common region interface and subsequent resource-plan boundary. The earlier architecture and coverage plans are historical checkpoints. [Regional architecture](39-regional-sync-architecture.md) · [Integration plan](41-general-autosync-architecture-plan.md)

## From accesses to an executable plan

1. **Construct demands.** For each admitted execution, an earlier conflicting access must complete before the later payload issues. Conflicts include read-after-write, write-after-read and write-after-write on overlapping physical bytes, subject to the selected native guarantees. Include supplied ordering constraints. The exact route reduces demands relative to its admitted access model and native order. The conservative route propagates possible outstanding accesses and guaranteed deliveries across branches and loop backedges, including the zero-trip path.
2. **Choose captures and waits.** A logical completion token can serve several consumers. A pipe-prefix record captures the work issued on its pipe up to that cut and the completions already acquired there. The consumer must receive the required prefix before its first conflicting issue. An earlier capture can free later independent producers, but every subsequent consumer that relied on the original prefix still needs its prerequisite. A same-pipe hazard may require a local barrier.
3. **Allocate and emit.** A hardware wait consumes a publication. Reuse of an event ID requires the previous consumption to precede the next publication on that direction and execution instance. Account for native reservations, generated reverse acknowledgments, skipped visits and invocation closure. A repair that adds order or guarded commands needs a new feasibility check. Ownership is transactional on refusal. In per-function mode PTOAS may still run with insertion enabled and skip explicitly synchronized functions. [Physical realization](15-physical-demand-realization.md) · [RealizeSync](../passes/59-realize_sync.md)

**Implemented routes.** The public token route uses `InsertSync → OptimizeSync → LowerSync`, coordinated by `RealizeSync`. Lowering interprets the actual tokens and performs physical planning. Peer planning also has a finite route that allocates directly and a structured route that exports logical prefixes. A change to storage, native variant, payload order, control or target invalidates any proof that depends on it. ## Contract between a region and its parent

Section 8 of the draft distinguishes selective composition, conservative prefix entry wrappers and regional completion. In the exact selective construction (section 5), each physical storage class respected by writes exports its first and last writer, its first reader per pipe before the first write, and its last reader per pipe after the last write. A class with no writer exports the first and last readers per pipe. The child also exposes boundary occurrence identities and queries about which issue and completion events precede which others, including native ordering. These let a parent construct and reduce crossing demands. In the conservative construction (section 6), the parent can keep a closed child’s commands and wrap its entry using sound per-pipe access summaries under the stated entry conditions. Removing a wrapper on the strength of an internal wait requires proof that the wait delivers the incoming completion before the conflicting issue. Regional completion can instead propagate a closed fragment’s summary of accesses around a common completion. The branch’s per-pipe completion summary records different facts. A caller requests only the capabilities its proof uses.

| Boundary | Proposed common interface for finite and structured planning |
| --- | --- |
| Entry and first use | Identify possible physical accesses, their issuing pipes, and the original issue cuts that can first conflict with incoming work. At each cut describe the incoming completions guaranteed by internal records and waits on every path reaching it. Tie each capture to its producer occurrence. |
| Exit and repetition | Export what each pipe has definitely acquired and which accesses can remain outstanding, including readers of individual rotating slots. At a join retain possible obligations from either arm and only guarantees valid on every reaching path. Include skipped iterations, wraparound and epilogue uses. |
| Physical resources | Once resources are planned, expose directional claims, reservations, generated acknowledgments and consumption obligations crossing the boundary. A parent that changes a handoff must recheck storage ordering, event matching, causal reuse and progress under the authored protocol assumptions. |

**Implemented today.** The compact exact analysis selects boundary readers and writers, reduces crossing demands and answers reachability between issue and completion events. Conservative analysis has a per-pipe exit summary, retained-child resource information, and per-issue entry checks for qualified straight-line inlined children. Those entry checks inspect the logical recipe and certify proposed deletions together on the parent control-flow graph with other services fixed. [Compact composition](../../../../src/ir/transforms/utils/compact_sync_analysis.cpp) · [Completion summary](../../../../src/ir/transforms/utils/conservative_sync_completion.h) · [Entry and exit analysis](../../../../src/ir/transforms/utils/conservative_sync_dataflow.cpp)

**Proposed common contract.** A result identifies its physical storage partition, original occurrence coordinates, admitted execution context and the order that a query describes (required payload order, selected logical order or emitted command order). A selector can return an occurrence, prove its absence or report missing evidence. Reachability between present endpoints is a separate question. Reuse the exact selectors and the conservative summaries through this interface. Return an unmet obligation when a structurally applicable route lacks a requested proof. [Regional query contracts](39-regional-sync-architecture.md)

**When an entry wrapper is legal.** The retained visit must have closed logical event matching, a legal entry cut with ready guard values, and protection for supplied non-storage prerequisites. Physical import must also establish event ownership and consumption before reuse. For example, a SET in one iteration consumed by a WAIT in the next can allow retaining the whole loop while ruling out wrapping each iteration. If the chosen boundary fails these conditions, try an enclosing qualified boundary or report the unmet obligation.

### Two acceptance cases

**Prefill merge.** Three loads fill the current input tiles. In the accumulation arm, three more loads fill disjoint tiles before the first vector consumer, `TMAX`. The internal MTE2→V wait at that consumer covers both groups. The parent can drop an entry flag pair and an MTE2 barrier if replay also covers subsequent uses and event reuse. This frees nine load-completion-to-load-issue pairs per active accumulation. Moving a load destination onto the prefetched bytes must restore the same-pipe order. Initialization and skipped work exercise separate paths. [Guarded alias regression](../../../../tests/ut/ir/transforms/test_automatic_sync_children.py)

**Two-stage receive pipeline.** With two local Mat slots, executed pop number `k` (counting from zero) writes the slot at `base + (k % 2) * slot_stride`. A view of the popped tile keeps that binding when the cursor advances. An MTE1 move reading slot 0 must finish before a later MTE2 pop overwrites slot 0, even when that pop is in the epilogue. Free closes the logical borrow while its asynchronous reader may still be active. A skipped pop leaves the cursor in place. The current planner can deliver completion after the last reader. A more selective plan would capture there and wait at the first actual overwrite, provided it can prove the correct slot and safe event reuse on every path. Test an unrelated move that should remain in flight as well as the required reader-before-overwrite edge. [Slot-order regressions](../../../../tests/ut/ir/transforms/test_peer_loop_slot_order.py)

## Alignment with the synchronization draft

The reference is *Synchronization for Reused Physical Storage*, manuscript revision `7f2f244`, main sections 3–8 under `paper/sections/`. Sections 3–5 fix the payload program, define the required completion-to-issue relation and reduce exact demands. The direct-insertion leastness result has premises, including adjacency of indispensable same-pipe requirements. Section 6 gives conservative coverage and explains why omitting child-entry synchronization using internal deliveries needs a stronger interface than a union of accesses. Section 7 separates fixed-plan allocation from repairs that may add order. Section 8 composes the logical and physical phases. The branch implements qualified instances of these constructions. Global minimality across all admitted conservative and finite-resource plans remains unproved. [Draft repository](https://github.com/tonibohnlein/synchronization_draft)

Compare plans at fixed payload order, operands, physical placement, alias assumptions and invocation boundaries. For execution `e`, consumer occurrence `b` and pipe `p`, `K(e,b,p)` is the rank of the last payload on `p` whose completion must precede `b`’s issue, or zero for an empty prefix. The draft calls the required profile `K₀` and the profile induced by plan `Σ` `KΣ`. A plan dominates another when every such entry is at most the corresponding entry in the other plan. Sum the difference against the required profile to measure excess when that profile is known. Against stock, report separately the pairs each plan adds over the other. A plan that frees a pop while delaying a later load can have a smaller total and still be incomparable. Report static and executed flags, barriers and guards separately. Device timing answers the latency question.

## Alignment with RFC #3375

| RFC boundary | Current branch and intended direction |
| --- | --- |
| Capture and normalization | In the RFC, `with pl.sync.record(after=t) as done:` captures a body. The optional `after` constrains entry, and `done` denotes its completion. Tokens from different pipes can be joined. The branch exposes pipe-prefix records and same-pipe joins. General composition of user records with automatic constraints remains open. Authored transport commands already survive local planning. |
| Dependency construction and simplification | The branch builds demands after placement and simplifies logical tokens. The RFC separates region normalization, dependency insertion, local canonicalization and control-flow simplification, then repeats canonicalization. Minimum-demand reduction belongs to analysis. RFC canonicalization uses local token equivalences. |
| Binding, planning and lowering | The branch selects native pipes during qualification and plans resources inside physical lowering or the finite peer route. The RFC assigns pipe binding to `BindSyncPipes`, resource planning to `PlanSyncResources`, and emission of the verified placement to `LowerSync`. A shared region contract is the next step. A target-qualified, serializable placement with ordered actions and guards is a later milestone. |

Preserve independent checks at each boundary. Compare equivalent views and alias controls at the effect boundary, replay payload order and event lifetimes at the plan boundary, and check the emitted ownership manifest against compilation with downstream insertion disabled. Device goldens and timings then test the code that actually ran.
